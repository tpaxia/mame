# GO011 experimental video-memory card

<!-- copyright-holders: Salvatore Paxia -->

Enable with `-bus:video go011`. The default slot is empty. This is an optional
non-DMA board at development priority position8, below the existing cards;
that index is not a claimed chassis connector number. STAC-2 printed31 assigns
minimum expansion priority to GO011. The card claims no main-memory addresses.

This increment implements local storage transactions and a **diagnostic
framebuffer screen**, not a fully functioning monitor. Control/status,
blanking/reversal, pointer overlay and interrupt behavior remain incomplete
and must not be represented by successful no-ops.

The diagnostic screen is560×410 at nominal42.52Hz. The graphics manual
3976460 A, PDF22/116, distinguishes the392-line graphics page from two lower
text rows. Identical GTL/native firmware tables place their glyph scan lines
at393–399 and403–409, using70bytes per row. The renderer shows written RAM,
high bit first; unknown storage appears black without becoming readable by
the CPU. It neither generates status/interrupts nor bypasses unsupported08.
See outer `analysis/hardware/video/raster-and-pointer.md` for evidence and
the still-unverified PROM timing hypothesis. No character-ROM substitution
or host-generated text is used. MAME's screen views expose the framebuffer
when the optional card is installed.

## Implemented contract and evidence

Source firmware: GTL4.1 P6FWO and native P6066 master068 K0E002/K0E003.
Overlay addresses below are relative word offsets, not relocated runtime PCs.
The outer repository's `analysis/hardware/video/` contains source hashes,
version-specific entry points, manuals and complete evidence notes.

| Transaction | Implemented behavior | Evidence / limits |
|---|---|---|
| ESE FF | Direct selection; other values deselect | Firmware writesFF to byte0088 before ESE. Other select aliases are not established. |
| CAE, full word0000–7FFF | Set local byte address | Live probe uses7FFE; overlay4 +0024 onward clears starting at0000 with count7FFF. DRAM bank consistent with32KiB. Upper-bit decode/wrap is unknown and rejected. |
| DAE58xx, full word | Store xx at the addressed byte | Live7FFE/A5 test and overlay3 +02AB..02C1 pixel RMW. Resulting address is marked unknown: next access needs CAE. No increment/hold guess. |
| EDA/EDB input | Read the addressed stored byte, without advancing | Live probe; overlay4 +005A..005F addressed read loop; overlay3 +02E6..02E8 reads before each streaming write. |
| DEA with high18, maskFF00 | Read addressed data through normal input callback | Overlay3 +02B1..02BA, then modify and58-write the same byte. Full-word18 wiring is not established. |
| DAE54xx, full word | Store and advance to the next byte | Overlay4 clear loop and overlay3 raster transfer,70 bytes per row. Do not wrap after7FFF: a further access requires explicit CAE. |

There is **no special case for A5 or7FFE**. All bytes use the same storage.
Byte-read and DMA behavior are separate: the card does not request DMA or
invent refresh reads from host RAM. No interrupt source is implemented yet.

`written` and `address_known` are **emulator coverage guards**, not physical
board bits. Unwritten/reset-uncertain RAM reads terminate with an explicit
diagnostic rather than return a fabricated initial value. Selection changes
invalidate address confidence. Reset clears confidence and selection, not RAM
contents; no physical RAM clear or retention rule is asserted. These guards
are intentionally restrictive and must be replaced as hardware evidence grows.

RAM, address, selection/reset state and coverage guards are registered for
MAME save states. Live save/load round-trip remains unverified.

## Explicitly unsupported

All selectors other than54,58, the inferred coordinate ranges0C–13, and the high-byte-only18 read cycle fail with
`GO011 evidence boundary`, including00,04,08,1C,38,98 and unclassified forms.
Name/type/status reads, standalone ECOT and channel controls also fail. The
08 operation after successful startup detection is therefore an expected
boundary, already identified statically before this implementation. Timing
PROM wiring and reset/status/IRQ truth tables remain in the outer `TBD.md`.

This is the user-authorized first storage milestone, not hardware acceptance
or a claim that every video operation is emulated.

## Validation

`python3 scripts/puce/test_go011.py` compiles the production CPU channel core,
bus routing methods and card callbacks, with only MAME plumbing stubbed.
An address-derived independent oracle fills all32768 addresses in permuted
order and reads them linearly;1792 boundary/value cases include every byte
value, followed by full-aperture streaming and readback. Tests cover RMW with
DEA lane masks, every partial write/address mask, rejected upper addresses,
all other selector values, deselection/removal, interrupt-channel isolation,
reset uncertainty and unknown initial data. Ordinary byte values, not only
the boot signature, are required to survive the actual callbacks.


## Inferred pointer coordinate latches

The optional card now accepts full-word DAE0C00–0FFF and1000–13FF as two
10-bit coordinate counters. Native firmware encodes horizontal position as
`1023-x` and vertical position as `y+10`. The independent M40 graphics extension
confirms pointer coordinates,560×392 bounds, movement and off-screen parking;
it does not use the GO011 wire encoding. This is a functional inference from
software, not schematic verification of every selector bit.

The raw counters and validity guards are saved. Reset invalidates confidence;
coordinate writes invalidate RAM-address confidence. All1024 counter values
are retained without clipping, including off-screen positions. Partial-lane
coordinate writes are rejected. The renderer still presents RAM only: pointer
visibility/brightness is not guessed, and control08 still stops explicitly.

Production CPU/bus/card tests cover all219520 visible coordinate pairs, all
1024 raw values per counter, all partial masks, and reset confidence. The
outer evidence is `analysis/hardware/video/m40-crosscheck.md` and
`control-pair-results.json`. These tests validate the inferred latch model;
they do not establish enable, blanking, status timing or physical bit decode.

## Functional-control milestone (supersedes the earlier08 boundary)

The user requested behavioral compatibility rather than electrical reconstruction.
The card now uses an explicit inferred control model:08 establishes normal
unblanked control state while preserving RAM/coordinates;38 ends an access;
1C toggles inversion (native command06 matched to M40's reverse toggle).
00/98 select blanked/unblanked output provisionally, based on their paired
M40 operation5 calls; polarity/effect needs a dedicated guest test. The latter
pair is not established by the successful startup below. Control writes are
counted and their mode is saved, along with inversion/blanking state.

Implemented operations complete synchronously. Name/type returns00F0: logical
nameF and idle status (including busy bit0 clear). This is a functional timing
abstraction, not a hardware timing claim. Unsupported04 scrolling still stops;
it has not been represented as a successful idle transaction. Pointer visibility
is still not rendered, although coordinate latches exist.

Native P6066 compilation disk now boots to READY on both console and GO011's
actual560×410 framebuffer and runs60 emulated seconds without a device exception.
Ordinary keyboard input of BASIC is echoed on video, followed by guest ERROR190;
that is not a successful BASIC launch. GTL4.1 CONFIGURE EXD still returns168.
Artifacts and raw-screen captures are in outer `analysis/hardware/video/functional-native/`.
The prior expected-stop description at08 and status no longer describes this
revision. These guest results validate startup and status-row text, not every
control, graphics primitive, pointer or scrolling operation.

## Functional scrolling

DAE high04 now applies CAE as a signed15-bit byte displacement to the
560×392 graphics page. Negative displacements move content toward the top;
7D44 means−700 bytes, ten70-byte rows. The two service rows and remaining
local RAM are preserved. Exposed page bytes become zero; ESE's subsequent
1046-byte clear at675C remains a separate guest operation. The low DAE byte
is not used as a second displacement. The model retains source validity for
moved bytes and invalidates the transfer address afterward.

This is an inferred black-box model, not a claim of a physical RAM-copy
circuit. Completion is atomic, matching the functional status abstraction;
ETIB busy is clear after the copy. Up/down/zero and multiple-row displacements
are tested through production CPU/bus/card callbacks against an independent
page-pattern oracle; every RAM byte is checked, including service storage.

Native ESE was booted and given CATALOG three times through normal keyboard
input. All three issued0444 and completed without the former fatal exception.
The run continued110 emulated seconds, exit0. The video capture contains the
catalogue line and READY. See outer
`analysis/hardware/video/functional-native/video-scroll.png`,
`scroll-results.json`, and `scroll-video-bus.txt`. This establishes the observed
scroll command path; it does not establish hardware busy duration or all
possible graphics uses of04. Earlier notes calling04 unsupported are historical.

## CRT presentation

The original-machine video `P6066_Facebook_1092391199216223.mp4` shows green
phosphor text rather than white. The renderer now draws firmware RAM pixels in
green on black. Its previous five-pixel blinking underline was generated solely
by the emulator from coordinate latches, not by video RAM. It is disabled:
the filmed READY/CAT/ENV presentation does not show that underline normally.
The coordinate latches remain available to the guest; graphics pointer
rendering is still unresolved. The General Manual PDF599 mentions an input
cursor, so its exact hardware circumstances remain open. Older cursor-on/off
captures in the outer repository document the removed approximation, not the
current renderer.

The same film suggests CAT/ENV output takes roughly half the time seen in the
current video-enabled emulator, but the camera does not continuously show both
input and completion for a calibrated measurement. The CPU still uses a
provisional 1 MHz scheduling clock and incomplete instruction/memory timing.
This is a timing discrepancy to investigate, not a basis for doubling the
machine clock or bypassing guest-driven video writes.

## Window layouts

With `-bus:video go011`, the default layout is **Video and Console**: the
560×410 video above a smaller console with its display, lamps and mouse controls.
The complete layout scales proportionally when the window is resized; controls
do not retain a fixed pixel size. Without GO011, the default is **Console**.
Saved UI settings or explicit `-view` options can override the initial choice.

For one window, use `-numscreens 1 -view "Video and Console"`.
For separate windows, use `-numscreens 2 -view0 Video -view1 Console`.
The views can also be selected through MAME's Video Options menu (enable UI
controls with F12, then press Tab). **Video** and **Console** remain individually
selectable in the combined configuration.
